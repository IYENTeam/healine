## Data flow

```text
Polar AccessLink v4 → existing Apps Script → Healine DB
                                             ↓
Google Calendar ← existing Apps Script ← persisted observations
```

Apps Script retains Polar authorization and Calendar writes. Healine stores the
resource responses before processing, normalizes shared health records, retries
processing failures, and exposes collection diagnostics. Source and tests live in
`integrations/polar-calendar/`. The inherited Polar v3 connector remains separate;
pairing this collector does not require a second Polar connection.

## Start the local platform

Configure `backend/config/.env` using the [Docker guide](/deployment/docker),
including a private `SECRET_KEY` and administrator password. Set
`COLLECTOR_PUBLIC_URL` to the collector's fixed HTTPS origin and
`COLLECTOR_SETUP_URL` to the existing Apps Script deployment URL ending in `/exec`.

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build \
  db redis app celery-worker celery-beat frontend collector-ingress
```

The portal is at `http://localhost:3000`, the API at `http://localhost:8000`,
PostgreSQL at `127.0.0.1:55432`, and Redis at `127.0.0.1:56379`. Put an HTTPS proxy
or named tunnel in front of port 8011. That ingress allows only the three collector
routes; keep the administrator API local. PostgreSQL and Redis use persistent
volumes. `down -v` removes those volumes and must not be used to restart services.

Temporary tunnel URLs are for connection testing: they may change and stop when
the tunnel process exits ([Cloudflare Quick Tunnel limits](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/do-more-with-tunnels/trycloudflare/)). Ongoing operation requires a fixed address, and this
local installation requires the Mac and Docker to remain awake and running.

## Connect the existing Apps Script

1. Run `integrations/polar-calendar/scripts/deploy-existing.sh --apply "Connect Healine platform"`.
   Its validator checks the fixed project and deployment, nine-file upload set,
   syntax, and Node tests. These deployment targets belong to the existing installation.
2. Sign in to the local portal, open the intended user's profile, and issue a code
   under **Polar 수집기 · 캘린더 연결**.
3. Copy the code and open the linked Google setup screen. Confirm the server
   address, paste the code, and submit. Codes work once and expire after 15 minutes.
4. Apps Script privately stores the returned collector key and runs its first sync.

For the configured local administrator, a private handoff can also be prepared:

```bash
backend/.venv/bin/python integrations/polar-calendar/scripts/prepare-local-pairing.py
```

Open the printed HTML file in a browser. This helper uses the administrator
credentials in memory and writes a private file containing a short-lived pairing
code. Rerun it if the code expires. Issuing a code leaves the old key valid;
consuming the code rotates that key.

Existing Polar credentials, the calendar, event identifiers, and personal notes
are retained. Before pairing, standalone collection continues. After pairing, platform errors preserve existing entries. A Polar authorization failure can still render retained platform observations, with a visible collection warning and actual measurement dates.

## Verify real operation

The collector card must show a recent receipt and dated results for heart rate,
activity, sleep, and recovery. Inspect each result and sample count: receipt alone
does not prove successful normalization. The daily calendar description should
include **수집 상태 · Healine에 저장된 기록**.

Shared timeseries store heart rate, steps, and MET under provider `polar`, source
`polar_accesslink_v4`. Sleep appears in sleep events; Polar sleep and recovery
values appear in health scores. The dedicated collector card reports the edge
connection; the legacy OAuth provider list is independent.

Do not declare the transition complete until real Polar responses are stored and
a calendar refresh reads those persisted observations.

## Calendar records for later analysis

The calendar is the user-facing timeline. Each observed hour contains readable
quarter-hour measurements and a versioned `[HEALINE_DATA_V1]` JSON block with up
to 60 observed minute buckets, explicit units, actual measurement timestamps,
coverage and personal comparison evidence. Daily events include dated recovery,
sleep, hourly trends and collection status. No dashboard or check-in is required.

Missing measurements remain `null`; recorded zero steps remain zero, including
hours with no heart-rate samples. Empty minutes are not interpolated. Hourly
heart rate is the median of quarter-hour medians, and its range comes from the
observed samples. Raw responses remain in Healine. See the
[calendar data contract](https://github.com/IYENTeam/healine/blob/feat/polar-calendar-integration/integrations/polar-calendar/README.md#캘린더에서-후속-분석하기)
for the fields and aggregation rules. Notes under `[내 메모]` survive updates in
both daily and hourly events.

Descriptions plus notes are bounded to 8,000 characters. Long hourly records use
shorter prose while retaining the same JSON observations and comparison evidence.
If preserved notes still exceed the budget, the writer stops before mutation.
The readback audit uses event tags, so a truncated description cannot disappear
from the audit simply because its closing marker is missing.

An existing hourly event whose observations disappear from a successful snapshot
is updated to explicit missing data, preserving its notes; a fetch error leaves
the previous records intact. Legacy quarter-hour events are retained because
their generated text cannot be reliably distinguished from user annotations.

## Missing data, backfill, and replay

Each response stores its original HTTP status and JSON body. Identical daily
responses reuse the same batch. HTTP errors, empty dates, absent detailed samples,
invalid samples, and unexpected structures have distinct diagnostics. Missing
samples never become zero-valued observations.

The live Polar REST gateway can return `heartRateSamplesPerDay` and `activityDays`
directly at the root. Normalization accepts these observed forms as well as the
wrapper objects in the published Swagger contract. Unknown nonempty structures
still produce a parse error. The saved raw responses make it possible to repair
and replay a shape mismatch without another authorization or provider request.

Calendar queries use the latest successful snapshot per date/type, with diagnostics
from the latest fetch. A later empty or failed response retains earlier observations.
Replaying an older response cannot erase that fallback or overwrite newer records.

The existing 15-minute trigger rereads today and yesterday and reconciles one older
date from a rolling 30-day range or the explicit backfill queue. Reconciliation
includes Calendar writes, not just platform ingestion. Failed dates remain pending
with bounded exponential delay while other dates continue. A successful date
invalidates recent comparison references so late data can affect later displays.

Use `queueHealineBackfill(from, to)` for an exclusive-end range of up to 60 days;
without arguments it queues the last 30 days. `continueHealineBackfill()` processes
up to four dates and stops starting dates after a 240-second budget.
`replayStoredHealineCalendar()` uses only retained data when Polar cannot be
reauthorized yet. Inspect `getHealineStatus()` for pending dates, attempts, latest
backfill mode and collection errors. Cached replay is not a successful new provider
fetch. Unreceived periods cannot be recreated without source data.

Calendar creation throttling pauses all Calendar writes until the persisted
`calendarRetryAt` deadline, including cached replay; source collection can
continue. English and Korean creation-limit messages are recognized. The latest failure records its stage and message. Do not clear this
deadline to force repeated attempts during a service restriction.

An `invalid_grant` blocks repeated token refresh attempts until the owner
reconnects through the same web app. Daily Calendar records show the interruption
and retain known measurements. Successful reauthorization records a durable
catch-up request; the next live run queues the latest 30 days and clears source
retry delays while preserving Calendar cooldown. A cached replay in progress
cannot consume that fresh-source request.

Token exchange, refresh and persistence share a short script lock, separate from
the collector's user lock. A delayed 401 reuses a concurrently replaced token;
an older generation's failed refresh cannot disable a newer authorization.
`getHealineStatus().tokenLifecycle` contains only timestamps, generation/counter,
replacement status and HTTP/OAuth error codes. Credentials and provider error
descriptions are never written to diagnostics. `verifyPolarAuthorization()`
performs a real refresh and recovery API request, then reports sanitized metadata.
Use it after an authorization repair; it changes the stored token as a normal
refresh does. Transient service errors preserve credentials and remain retryable.
The `invalid_grant` code alone does not distinguish expiry, revocation or a
credential race. Do not promise that a revoked grant can recover without consent.
Sleep/ANS components are rehydrated from retained
raw snapshots on read, including successful snapshots behind newer failures;
no destructive historical migration is required.
Watch-to-Flow synchronization still determines when new data becomes available.

Pending processing and internal failures retry every 60 seconds, up to five
attempts. After fixing a parser, use **저장한 응답 재처리** on the collector card.
Replaying an HTTP error cannot fetch fresh Polar data. See the
[collector API](/api-reference/collectors) for authentication and response contracts.

## Maintenance and limits

```bash
docker compose -f docker-compose.yml -f docker-compose.local.yml ps
docker compose -f docker-compose.yml -f docker-compose.local.yml logs --tail=50 app celery-worker
docker compose -f docker-compose.yml -f docker-compose.local.yml restart app celery-worker celery-beat
```

Back up PostgreSQL before upgrades. Raw batches remain until the owning user is
deleted; automated raw-batch retention is not implemented. Shared-record retention
does not remove these batches. Portal status responses omit raw health payloads.

Dates currently use Asia/Seoul. Sleep interval length includes interruptions and
is stored as time in bed, without inventing net sleep time. Shared timeseries are
upserted by timestamp; omission from a later snapshot does not delete an earlier
sample from shared history. Calendar queries use complete stored snapshots.

## Fixed ingress for this installation

The existing local installation uses `https://healine.iyendev.com`, a dedicated
named Cloudflare tunnel to the collector-only ingress at `127.0.0.1:8011`.
`COLLECTOR_PUBLIC_URL` and the collector's stored origin must agree. The operator
function `repairHealinePlatformConnection()` checks the configured fixed origin
using the existing collector key, rolls back on failure, and queues recent history.
It does not replace the OAuth client, key, Apps Script project or Calendar.

The dedicated macOS launch agent is `com.iyendev.healine-collector`; its tunnel
configuration is `~/.cloudflared/healine-collector.yml`. It restarts the tunnel
process after a crash and at user login. It does not wake the Mac or start Docker.
Check an unauthenticated collector request returns 401 and an administrator API
path returns 404. Keep credentials outside the repository. Never use a random
Quick Tunnel address as the long-term collector origin.

## Recovery and comparison model

Calendar model version 3 includes Polar ANS rating, signed ANS status, sleep
component scores and separate prior-night comparisons. Daytime comparisons match
current and previous activity with past observations near the same time of day.
Read the [exact display rules](../../integrations/polar-calendar/README.md) and
[research and SDK assessment](./polar-calendar-evidence.mdx). Verification of
aggregation, missingness, time order and recoverability is separate from any
validation of psychological stress detection.
